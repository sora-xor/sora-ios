# Recovery routing, retained data and in-place repair

Integration work dated 12 October 2026. This file records implemented behavior
and remaining qualification; it does not claim release readiness.

## Routing and truthful actions

Startup classifies an absent account database using actual Keychain wallet-key
tags. A saved PIN or username alone does not count. Stale wallet defaults and
network metadata are preserved locally before normal onboarding (no keys) or
Welcome back (retained keys). SQLite companions, migration/account journals and
unreadable pending-transfer records stay on recovery paths. Classification is
rechecked under the lifecycle lease so an account committed while acquisition
waited cannot be moved as stale metadata.

Recovery text and visible actions use the same option flags, including direct
phrase and Google Drive actions. Welcome back enters the requested import flow
after its explicit set-aside confirmation. A first legacy-upgrade failure can
be retried on the same interactor; account-switch recovery has a real startup
retry. The tab-bar recovery route can also preserve old data and start restore.

Missing credentials retain the add-only restore route. Invalid retained keys
open authenticated repair with phrase, seed, JSON or Google Drive. Each Drive
source is independently proved against the actual account; a stale phrase or
seed does not hide valid JSON. Ordinary import of an existing account opens
repair with the supplied fields instead of ending at duplicate-account failure.
See `credential-repair.md` for the durable quarantine transaction, manual PIN
requirements, recovery gate and the remaining no-row import case.

Read-only status is visible in the account picker and selected wallet header,
with its reason and a restore action. Explicit watch-only status stays distinct
and is never upgraded by key proof. Send and QR entry points check capability
before presenting a transfer form and reject stale account-selection callbacks.
Signing still performs all independent authentication and identity checks.

## Returning earlier data

Set-aside roots are excluded from backup, with attribute read-back before any
copy or move. The migration safety manifest stores a derivation-path digest;
legacy plaintext manifests remain readable for compatibility.

A completed preserved generation records hashes of its allowlisted files and
wallet defaults. Incomplete or ambiguous mixed-generation folders remain
preserved but are not offered for blind return. Onboarding and Welcome back
offer complete generations while live wallet state is empty. The public
account inventory is read from a temporary copy, since even read-only SQLite
can create SHM files.

Returning retained signing material requires manually verified owner-PIN
bindings, followed by an explicitly chosen new app PIN. Unbound 3.8.6 leftovers
still require phrase or Drive recovery; a stored app PIN is never an ownership
grant. PIN publication uses the existing durable rotation transaction and is
blocked while a credential repair remains pending.

A durable return plan and device-only Keychain receipt bind the folder and file
hashes before the first move. Restart verifies the entire generation on either
side of the move before resuming. Live destinations cannot be overwritten or
mixed into the return. Only allowlisted wallet defaults are restored, with
read-back. Normal startup verification follows; no signing secret is rewritten
by the file return.

## Downgrade preservation

Recovery runs a narrowly scoped add-only copy for legacy global entropy that
proves an actual SORA2 row. It skips watch-only accounts, incompatible paths and
conflicting existing material, writes entropy/seed/direct-key copies with
read-back, and retains the original global entropy. This does not clear a
recovery marker, bind ownership or authorize signing. A regression exercises
the 3.8.6 global-deletion behavior after these scoped copies exist.
